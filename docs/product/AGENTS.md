# Product spec agentic instructions

- Keep `product-spec.md` as the source of truth for high-level product intent across console, CLI, and APIs.
- Follow the shared content and writing rules in `../AGENTS.md`.
- Organize by purpose/users, product principles, capability areas, broad delivery stages, non-goals, and uncommitted direction/open decisions.
- Describe user outcomes, meaningful product constraints, and supported kinds of work—not how individual screens or endpoints implement them.
- Keep capability descriptions independent of UI layout. Exclude exact labels, fields, pixels, animations, inspector structure, interaction recipes, API contracts, and backend algorithms.
- Own broad milestone outcomes here. Keep detailed task sequencing, POC exceptions, and current implementation progress in project/phase documents.
- Distinguish approved milestone scope from uncommitted candidates and architecture horizons. Do not promote candidates through wording changes.
- Reference `../architecture/architecture.md` for system responsibilities and technical boundaries rather than repeating them.
- Update the spec when user goals, major capabilities, product boundaries, non-goals, or milestone commitments change—not for routine UI or implementation changes.
- Preserve meaningful user-facing constraints while removing incidental detail; deleting a detailed sentence is not a product-behavior change.

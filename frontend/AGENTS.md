# Frontend agentic instructions

The console is a React app built with Vite, Tailwind and shadcn/ui, talking to the backend through
Connect-ES clients generated from `proto/`. `just --list frontend` lists the recipes, and
[`dev/AGENTS.md`](../dev/AGENTS.md) owns the development stack that runs it. These rules cover what
agents get wrong.

## Code map

```
frontend/src/
├── app/              app composition and providers; routes in routes.ts, router in router.tsx
├── routes/           route-level composition of features
├── features/         product capabilities and their behavior tests
│   └── chat/decisions/  the console chat's decision draft, controls and answers
├── components/
│   ├── ui/           primitives, from shadcn/ui or shared by several callers
│   └── <name>/       composites shared by several features
├── api/              hand-written Connect-ES transport and API adapters
├── gen/              generated Protobuf-ES code
├── hooks/            shared React hooks
├── panels/           inspector panel state and navigation
├── resource-watch/   live resource data streamed from the server
├── theme/            color scheme and resource colors
├── lib/              shared utilities with no UI
└── test/             shared Vitest and Testing Library setup, and repository-wide checks
```

- Routes compose features and don't reach into feature internals.
- A one-off treatment stays at its call site, not in `components/ui/`.
- A folder imports only from folders before it in this order: `gen`, `lib`, `api`, `hooks`,
  `panels`, `resource-watch`, `theme`, `components`, `features`, `routes`, `app`. `components/`
  also never imports `gen/`. Lint enforces this from the layer list in
  [`eslint.config.mjs`](eslint.config.mjs); folders marked `pending` there are not enforced yet.
- Files and feature folders never import each other in a loop, tests included.
  [`src/test/import-cycles.test.ts`](src/test/import-cycles.test.ts) enforces it, and its
  allowlists only shrink: fix a loop by moving the shared code down, never by adding an entry.
- Routes, features and components call `api/` and own no transport or protocol details.
- [`proto/AGENTS.md`](../proto/AGENTS.md) owns regenerating `gen/`.

## Running and checks

- Run `just frontend::bootstrap` once per workspace and after `package-lock.json` changes; the other
  recipes fail until then.
- `just frontend::check` runs the gate (format, lint, tests, build). Run it before completing
  frontend work.
- Run `just frontend::format` or `just frontend::lint-fix` only when their changes will be
  reviewed.
- The stack runs the frontend in `dev` mode (Vite with hot reload) or `nix` mode (the Nix-built
  frontend, copied to `.direnv/dotcore-frontend-nix` at each start: restart the frontend process to
  serve a new build). `DOTCORE_FRONTEND_RUN_MODE` picks it.
- Read endpoints from the environment variables the stack provides; never derive workspace ports
  in frontend code.
- `config.js` is the site's runtime config, generated by
  [`tools/runtime-config.mjs`](tools/runtime-config.mjs) before the server starts. It is untracked:
  change the tool, never the file.
- Never edit `dist/`, `coverage/` or `src/gen/`.
- With the browser tool, never read the response body of a console streaming request
  (`WatchMetrics`, `WatchResources` or any long-lived watch): it never completes and blocks every
  later browser call. Count streams from the request list, and read stream errors in the page or
  the backend logs.

## Dependencies

- Add packages with `npm install <pkg>` (`--save-dev` for development ones) and shadcn/ui
  components with `npm exec shadcn -- add <component>`. These are the only commands run outside
  `just`.
- Review `package.json` and `package-lock.json` together, then run `just frontend::bootstrap`.
- The Nix build ([`nix/frontend.nix`](../nix/frontend.nix)) reads its dependencies from
  `package-lock.json`. After changing the lockfile, check both builds with `nix build .#frontend`
  and `nix build .#frontend.tests.default`.

## Styling and components

- Check `src/components/` before writing UI. Reuse or extend a primitive or shared composite instead
  of writing a feature-local variant or layering custom CSS over it.
- Generated shadcn/ui primitives are customized in place; review a regenerated diff for local
  changes it replaced.
- Colors and other visual values are shadcn/ui tokens: define the raw value in `:root` and `.dark`,
  and map every one in `@theme inline` so it works as a Tailwind utility. An unmapped token is a
  bug.
- Add a scoped `--console-*` token only when no shadcn/ui token owns the value, with a comment
  saying why. Pointing an existing scoped token at its shadcn/ui owner beats adding a new one.
- Size controls and list rows in primitives with the density utilities (`h-control-*`,
  `h-menu-row*` and their `min-h-` and `size-` forms), never fixed heights, so touch devices get
  larger targets. Map a new or regenerated primitive's sizes onto them. A new density token also
  goes in `DENSITY_SIZE_NAMES` in `src/lib/utils.ts`; `src/test/design-tokens.test.ts` enforces it.
- Small isolated targets get `touch-target` inside their primitive, never in feature code. The
  element must be positioned (`relative` or `absolute`), not clipped by `overflow: hidden` on itself
  or an ancestor within the tap area, free of its own `::after`, and have room around it so
  neighbours keep their taps.
- Never add touch-specific classes (`pointer-coarse:`, `any-pointer-coarse:`) in feature code.
- Set sizes and spacing with Tailwind classes at the call site; the scale takes fractional steps,
  so most pixel values fit. Use an arbitrary value such as `text-[12.5px]` only when the scale
  can't express it, typically type size or line height.
- Keep a rule in `src/index.css` outside the Tailwind layers only when no utility can express it
  (a sibling combinator, scrollbar styling), with a comment saying why. Never add one to override a
  primitive's own utility: change the primitive.
- Use `cva` for a closed set of named looks, such as button variants. Use `data-*` attributes when
  the variation must reach descendants or reflects runtime state, such as a selected card.

## Behavior

- Show loading feedback through `useDelayedLoading` (`src/hooks/use-delayed-loading.ts`), so a fast
  read never flashes a loading state. While a refresh is pending, keep the last value on screen and
  switch to the loading look only when the hook says so; never draw from the raw pending flag.
- Draw metric visuals (bar rows, memory rows, history charts) empty at their final size as soon as
  their section mounts, not after the data arrives. Loading feedback only adds text inside them.
- Resource history (charts, range cards) always comes from metrics (`WatchMetrics`). Each kind of
  current deployment figure has one source across the console: VRAM from deployment status
  (`WatchResources`), app CPU and RAM from metrics. Read a new figure from the source its kind
  already uses, never from both.
- Every repeating read needs a stop condition: schedule it with `setTimeout` behind the state or
  open panel that needs it, clear the timer on unmount and dependency change, and pause while the
  page is hidden. Never use an always-on `setInterval` or a poll that outlives what displays its
  data.

## UI copy

- Keep labels, counts, notices and empty states short: the fact or the next action, such as
  `5 hidden` or `No profile runs here`. Never repeat what the view already shows, such as the active
  filters, the selected location or the sizing scenario.

## Form validation

Forms that validate before submit follow this timing, so tabbing through a field never flags it:

- Track the operator's changes with `useDirtyFields` (`src/hooks/use-dirty-fields.ts`). A field
  becomes dirty when the operator changes it, including picking or clearing a selection, and stays
  dirty until the form reopens or resets. A value derived from another field doesn't make it dirty.
- On blur, validate a field only if it is dirty.
- On change, re-validate a field only while it shows an error.
- On Next, Deploy or Save, validate every field of the step or form, show all errors, and focus the
  first invalid field with `focusFirstInvalidField` (`src/lib/form-validation.ts`).
